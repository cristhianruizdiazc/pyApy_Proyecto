## 1. Resumen Ejecutivo del Estado R3.4.2

La versión R3.4.2 representa la consolidación y endurecimiento estricto del desacoplamiento arquitectónico implementado en R3.4.1. Se verificó y cerró quirúrgicamente la superficie de ataque y los puntos críticos del sistema:

1. **Frontend 100% Desacoplado y Sin Persistencia Local:** Se confirmó la inexistencia absoluta de capas locales de almacenamiento (`localStorage`, `sessionStorage`, `IndexedDB`, `MarketplaceService`, `StorageService`, `AvailabilityService`, `mockData` o `seedData`) en `src/`. El frontend consume exclusivamente la API REST autoritativa a través de `ApiClient`.
2. **Endurecimiento de Reglas de Seguridad en Cloud Firestore (`firestore.rules`):** Se blindó la colección `/properties/{propertyId}` frente a escaladas de privilegios directas vía Firebase Client SDK. Todo propietario autenticado que intente crear una propiedad directamente queda forzado a `isVerified: false`, `isVip: false` y `verificationStatus: "pending"`. En las operaciones de actualización (`update`), se bloqueó la mutación directa de `isVerified`, `verificationStatus`, `verificationDate`, `verificationNotes`, `isVip`, `subscriptionPlan`, `rating` y `reviewsCount`.
3. **Validación Server-Side en Creación de Propiedades (`POST /api/properties`):** Tanto en `server/firestoreService.ts` como en `server/devAdapter.ts`, se impidió la inyección de privilegios administrativos (`isVerified`, `isVip`, `verificationStatus`, `subscriptionPlan`, `rating`, `reviewsCount`), forzando valores seguros autoritativos independientemente del payload suministrado por el cliente.
4. **Persistencia Autoritativa Fail-Closed en Producción:** En modo producción (`NODE_ENV=production`), `ProductionStorageAdapter` interactúa exclusivamente con Cloud Firestore. En caso de ausencia o fallo de conexión con Firestore, el backend responde con HTTP 503 (`SERVICE_UNAVAILABLE`) sin recurrir bajo ninguna circunstancia a memoria, archivos JSON o adaptadores de desarrollo.
5. **Limpieza de Empaquetado:** Se eliminaron archivos comprimidos anidados residuales (`pyapy-mvp-1.0-r3.4.1.zip`). El artefacto oficial final empaquetado es `pyapy-mvp-1.0-r3.4.2.zip`.

## 4. Estado Real de `firestore.rules`

Se auditó y endureció el bloque correspondiente al catálogo de propiedades:

```rules
    // PROPERTIES COLLECTION (Contains sensitive PII: ownerCi, ownerAddress, hostPhone, hostEmail, internalNotes)
    match /properties/{propertyId} {
      allow read: if isAuthenticated() && (resource.data.ownerId == request.auth.uid || isAdmin());
      allow create: if isAuthenticated() && (
        isAdmin() || (
          request.resource.data.ownerId == request.auth.uid &&
          request.resource.data.isVerified == false &&
          request.resource.data.isVip == false &&
          request.resource.data.verificationStatus == "pending"
        )
      );
      allow update: if isAuthenticated() && (
        isAdmin() || (
          resource.data.ownerId == request.auth.uid &&
          request.resource.data.ownerId == resource.data.ownerId &&
          request.resource.data.isVerified == resource.data.isVerified &&
          request.resource.data.verificationStatus == resource.data.verificationStatus &&
          request.resource.data.isVip == resource.data.isVip &&
          request.resource.data.get('verificationDate', null) == resource.data.get('verificationDate', null) &&
          request.resource.data.get('verificationNotes', null) == resource.data.get('verificationNotes', null) &&
          request.resource.data.get('subscriptionPlan', null) == resource.data.get('subscriptionPlan', null) &&
          request.resource.data.get('rating', 0) == resource.data.get('rating', 0) &&
          request.resource.data.get('reviewsCount', 0) == resource.data.get('reviewsCount', 0)
        )
      );
      allow delete: if isAdmin();
    }
```

### Justificación de las restricciones añadidas:
1. **Regla de Creación (`allow create`):** Un propietario normal sólo puede crear documentos donde `ownerId` coincida con su `auth.uid` y los campos de confianza pública queden obligatoriamente inicializados en estado neutral (`isVerified == false`, `isVip == false`, `verificationStatus == "pending"`). Únicamente un administrador (`isAdmin()`) puede eludir estas restricciones iniciales.
2. **Regla de Actualización (`allow update`):** El propietario no puede modificar el `ownerId` ni alterar métricas de confianza o datos administrativos (`isVerified`, `verificationStatus`, `isVip`, `verificationDate`, `verificationNotes`, `subscriptionPlan`, `rating`, `reviewsCount`).
3. **Colección `/reservations/{reservationId}`:** Se mantiene la directiva de seguridad de máxima prioridad:
   `allow create: if false; allow update: if false; allow delete: if false;`
   Ningún cliente puede escribir directamente en reservas; todas las operaciones de reserva requieren paso por el backend autoritativo con Firebase Admin SDK bajo transacción atómica.

## 8. Veredicto Final Técnico y Condiciones de Despliegue

### Veredicto:
🟢 **APROBADO PARA CIERRE TÉCNICO R3.4.2**

La arquitectura actual cumple rigurosamente con:
- React/UI → ApiClient → Express/Backend → Storage Adapter → Cloud Firestore.
- Ninguna capa de datos ni estado persistente local en el cliente.
- Prevención total de sobreventa mediante transacciones atómicas de reserva.
- Cierre estricto de vectores de escalada de privilegios en el modelo de propiedades.
- Arquitectura Fail-Closed en producción.

### Condiciones para Despliegue en Producción:
1. Definir en el entorno de Cloud Run o VPS las variables:
   - `NODE_ENV=production`
   - `FIREBASE_PROJECT_ID` o archivo de credenciales de Service Account (`GOOGLE_APPLICATION_CREDENTIALS`).
2. Desplegar `firestore.rules` al proyecto Firebase mediante Firebase CLI (`firebase deploy --only firestore:rules`) o la herramienta de plataforma `deploy_firebase`.
3. Ejecutar el comando de arranque: `npm start` (inicia `dist/server.cjs` compilado de forma optimizada y segura).
