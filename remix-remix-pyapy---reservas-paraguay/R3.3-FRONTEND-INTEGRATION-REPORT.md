**Versión:** pyApy MVP 1.0 — R3.3  
**Fecha:** Septiembre 2026  
**Entorno:** Google AI Studio / Cloud Run  
**Estado:** Integración Completada y Verificada  

---

## 1. Resumen Ejecutivo y Objetivo Cumplido

En la iteración R3.2 se implementó una base sólida de persistencia atómica, validación server-side, idempotencia y autenticación de roles en backend. Sin embargo, el frontend aún conservaba residuos arquitectónicos donde ciertos componentes leían o escribían en `MarketplaceService` y `StorageService` utilizando arrays en memoria y constantes locales (`SEED_*`).

El **objetivo único y estricto de la iteración R3.3** fue:
> **Convertir el frontend en un verdadero cliente del backend/API.**
>
> Arquitectura autoritativa obligatoria:
> ```
> FIRESTORE
>     ↓
> Backend / API (Express / Firestore Admin SDK)
>     ↓
> ApiClient (fetch centralizado con tokens y mapeo de errores HTTP)
>     ↓
> Frontend React (AppContext reactivo)
>     ↓
> UI / Componentes
> ```

---

## 2. Auditoría Forense de Fuentes de Datos (src/)

Se ejecutó un análisis exhaustivo en todo el árbol de código fuente `src/` para erradicar cualquier canal paralelo que actuara como fuente de verdad en producción:

| Elemento Auditado | Resultado Forense | Estado |
| :--- | :--- | :--- |
| `StorageService` | 0 llamadas en componentes de UI. Únicamente subsiste el archivo adaptador como puente transitorio pasivo. | **Deprecado / Limpio** |
| `SEED_*` constants | Ningún componente importa o consume datos de prueba. Restringido exclusivamente al inicializador dev/seed del backend. | **Aislado en Backend/Seed** |
| `localStorage` | 0 accesos directos para entidades de dominio (propiedades, reservas, bloqueos). | **Erradicado** |
| `sessionStorage` | 0 accesos directos en todo el proyecto. | **Erradicado** |
| `MarketplaceService` (mutaciones locales) | Eliminadas todas las mutaciones que salteaban la API. Todas las operaciones de creación/edición pasan por `ApiClient`. | **Unificado en ApiClient** |

## 3. Inventario de Componentes y Flujos Integrados

Todos los componentes de usuario, anfitrión y administración ahora interactúan exclusivamente a través de `ApiClient`:

### A. Flujo de Huéspedes / Clientes
1. **Catálogo de Alojamientos (`AppContext.tsx` & `PropertyList.tsx`):**
   - Hidratación inicial asíncrona al montar la aplicación vía `ApiClient.getProperties(filters)`.
   - Soporte reactivo de recarga (`reloadProperties()`) invocando la API tras cualquier mutación autoritativa.
2. **Creación de Reservas (`BookingModal.tsx`):**
   - Transmisión autoritativa mediante `ApiClient.createReservation({...})`.
   - El backend valida disponibilidad de turnos, calcula montos y seña en Guaraníes (Gs.), genera el código localizador (`PY-2026-XXXXX`), bloquea los turnos en Firestore y registra auditoría.
3. **Consulta y Localizador (`LookupReservationModal.tsx`):**
   - Búsqueda en tiempo real mediante `ApiClient.getReservationByLocator(locator)`.
   - Consulta directa a la colección `reservations` del backend sin dependencias locales.
4. **Demanda Insatisfecha y Radar Comercial (`WaitlistModal.tsx` & `SearchIntentModal.tsx`):**
   - Captura de fechas agotadas o solicitudes de zonas sin disponibilidad vía `ApiClient.createSearchIntent({...})`.
   - Persistencia directa en la colección `search_intents` para análisis y captación comercial de anfitriones.

### B. Flujo de Propietarios y Anfitriones
1. **Registro de Propiedades (`HostRegistrationModal.tsx`):**
   - Alta de quintas y cabañas mediante `ApiClient.createProperty({...})`.
   - Se descartó la manipulación directa de memoria; el alojamiento ingresa en estado `pending` para validación administrativa.
2. **Editor de Unidades y Planos (`FloorPlanEditor.tsx`):**
   - Actualización de distribución física y planos mediante `ApiClient.createProperty({...prop, units})`.
   - Persistencia inmediata en la base de datos centralizada.
3. **Panel del Propietario (`OwnerDashboard.tsx`):**
   - Carga de reservas del anfitrión vía `ApiClient.getOwnerReservations(propertyId)`.
   - Exportación oficial de reservas en formato CSV con firma del servidor vía `ApiClient.exportReservationsCsv(propertyId)`.
   - Indicadores de estado de reserva sincronizados con el ciclo de vida del backend.

### C. Flujo de Administración y Operaciones
1. **Panel de Control pyApy (`AdminDashboard.tsx`):**
   - Listado maestro de reservas cargado directamente desde el backend vía `ApiClient.getOwnerReservations()`.
   - Radar de demanda insatisfecha hidratado con datos reales vía `ApiClient.getSearchIntents()`.
   - Pista de auditoría operacional inmutable cargada vía `ApiClient.getAuditLogs()`.
   - Cambio de verificación de quintas mediante `ApiClient.updateVerification(propId, status, notes)`.
   - Actualización de planes de suscripción (Activo, Verificado, VIP) autoritativa en Firestore.

## 4. Robustecimiento de Errores HTTP y Resiliencia en Red

En `src/services/apiClient.ts` se implementó un traductor de códigos de estado HTTP que garantiza mensajes legibles, informativos y transparentes, sin silenciamiento de excepciones:

* **HTTP 401 (No Autorizado):**
  > *"Sesión no autorizada o expirada. Por favor, iniciá sesión nuevamente."*
* **HTTP 403 (Prohibido):**
  > *"No tenés los permisos necesarios para realizar esta acción."*
* **HTTP 409 (Conflicto de Disponibilidad / Idempotencia):**
  > *"Conflicto: La fecha u horario ya fue reservado por otro usuario. Por favor elegí otro turno."*
* **HTTP 422 (Entidad No Procesable):**
  > *"Datos incompletos o formato inválido en la solicitud."*
* **HTTP 500 (Error Interno del Servidor):**
  > *"Ocurrió un error en los servidores de pyApy. Nuestro equipo técnico fue notificado."*
* **HTTP 503 (Servicio No Disponible):**
  > *"El servicio se encuentra temporalmente en mantenimiento. Intentá nuevamente en unos instantes."*
